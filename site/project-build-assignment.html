Problem Set Handout

Problem Set: Full-Stack DER Decision-Support Tool

This handout specifies the implementation target for a cloud-deployed application that explores distributed energy resource and demographic patterns across regions.

You are not building a notebook demo. You are building a usable system with a data model, API, model outputs, grounded summaries, testing, deployment, and documentation.

1) Introduction

1.1) Objectives

Task. Implement a short project brief that names the user, the regional unit of analysis, the core decision-support question, and the final system you are building.
  • Design a region-centered data model for analytical applications.
  • Build a backend API that supports lookup, comparison, and summary generation.
  • Separate offline model computation from online application behavior.
  • Implement a grounded LLM workflow that retrieves evidence before generation.
  • Ship a tested, documented, deployable system instead of an analysis-only artifact.

1.2) Overview

Task. Implement one end-to-end user flow: select a region, retrieve metrics, view model-based insight, and request a grounded stakeholder summary.

Your application should let a user inspect one region, compare multiple regions, view DER and demographic indicators, access predictive or model-based insights, and request stakeholder-facing summaries backed by retrieved evidence.

The fastest way to fail this project is to design the interface first and improvise the rest. Start with the region entity, the schema, and the API contract. The frontend is downstream of those choices.

2) System Architecture

2.1) Data model

Task. Implement a normalized schema with a stable region_id and dedicated tables or objects for metrics, model outputs, evidence, and summaries.

Use region as the stable organizing unit. Every metric observation, model output, evidence object, and summary record should tie back to a region identifier.

Region-centered entity model

Region

region_id name zcta geometry_ref

MetricObservation

region_id metric_name value source

ModelOutput

region_id score_name score_value model_version

EvidenceChunk

evidence_id region_id text source_url

SummaryResponse

summary_id region_id evidence_ids[] generated_at 
Region(region_id, name, zcta, geometry_ref)
MetricObservation(region_id, metric_name, value, source, observed_at)
ModelOutput(region_id, score_name, score_value, model_version, assumptions)
EvidenceChunk(evidence_id, region_id, text, source_name, source_url)
SummaryResponse(summary_id, region_id, summary_text, evidence_ids, generated_at)

Store separately

Keep metric observations distinct from model outputs.

Track evidence

Every evidence record needs source metadata and a stable ID.

Persist summaries

Generated outputs should carry timestamps and evidence references.

2.2) Backend API

Task. Implement the required endpoint surface with typed responses and documented request and response contracts.

Define the API contract before you build every page. A strong system returns structured, typed responses. A weak system returns ad hoc JSON shaped around one UI component.

GET /regionsList searchable regions.
GET /regions/{id}Return region metrics and metadata.
GET /compareReturn comparison output for 2 or more regions.
GET /model-output/{id}Return stored predictive outputs.
POST /summariesGenerate a grounded stakeholder summary.
GET /healthReadiness and smoke endpoint.

2.3) Frontend contract

Task. Implement a frontend that renders region exploration, comparison, model outputs, and grounded summaries directly from structured API payloads.

The frontend should consume structured responses directly. At minimum, it should support region exploration, detail inspection, comparison, model display, and grounded summaries with visible evidence or citations.

3) Predictive and Grounded Components

3.1) Model pipeline

Task. Implement an offline feature engineering and scoring pipeline, persist the outputs, and expose those outputs through the application.

If you use predictive or model-based insights, compute them offline and store the outputs. Do not train or re-score large artifacts inside request handlers.

Offline model pipeline

Processed regional data
→
Feature engineering
→
Train or score
→
Persist outputs
→
Serve by API

3.2) Retrieval and summaries

Task. Implement a retrieval-first summary endpoint that returns generated text together with evidence IDs or citations.

A grounded summary feature is a retrieval pipeline with generation attached at the end.

Grounded summary flow

Receive summary request
→
Build retrieval query
→
Retrieve evidence
→
Assemble evidence set
→
Generate from evidence
→
Return citations

3.3) Guardrails

Task. Implement checks that block unsupported summaries, surface low-evidence cases, and preserve traceability from output text back to evidence.

Required behavior

  • Persist evidence IDs in the response.
  • Expose model or prompt version metadata.
  • Return a fallback when retrieval is weak.
  • Surface uncertainty or missing data.

Do not do this

  • Do not let the model invent evidence.
  • Do not call vague text a metric.
  • Do not hide missing values behind polished prose.
  • Do not treat the LLM as a database.

Minimum summary fields

summary_id
region_id
summary_text
evidence_ids[]
metric_snapshot
model_version
generated_at

4) Verification and Deployment

4.1) Testing

Task. Implement unit, integration, smoke, and regression tests that cover schema assumptions, API structure, UI-critical paths, and grounding behavior.

Your tests should cover both correctness and system integrity. If a summary can be produced without retrieved evidence, your tests are not strong enough.

Test type Schema API UI Grounding
Unit Yes Yes No Yes
Integration Yes Yes Yes Yes
Smoke No Yes Yes No
Regression Yes Yes No Yes

4.2) Deployment

Task. Implement a containerized cloud deployment with explicit configuration, a health endpoint, and a repeatable release path.

This project is a product, not only an analysis. Containerize it, deploy it to a stable cloud target, keep environment configuration explicit, and expose a smoke-check or health endpoint.

4.3) Documentation

Task. Implement documentation for setup, environment variables, API behavior, model assumptions, grounded summary behavior, and known failure modes.

Documentation must cover

  • local setup
  • environment variables
  • API surface or OpenAPI specification
  • model assumptions and limitations
  • grounded summary behavior
  • known failure modes

Definition of done

  • Deployed URL works.
  • Tests run from a clean clone.
  • API is documented.
  • Summary output exposes evidence.

5.2) Evaluation

Task. Perform a self-audit against the rubric and close any gap that would make the project feel like a notebook demo instead of a usable system.

Strong work has clear separation between data, API, modeling, and presentation; interpretable model outputs; grounded summaries with evidence traceability; reproducible testing and deployment; and documentation that another person can follow without asking for clarification.

Weak work collapses all logic into a notebook or one script, depends on undocumented joins, returns unsupported LLM output, or works only on the original author's machine.

Common failure modes

  • Region identifiers drift across layers.
  • Summary generation runs without evidence.
  • The application works only on the author's machine.
